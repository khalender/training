Résumé
Dans la pratique, il est impossible d’écrire directement un programme sans faute.
Une étape importante de tout développement d’application est de détecter l’en-
semble des erreurs qu’il contient pour pouvoir les corriger.
La notion d’erreur englobe différents concepts. Ici, nous nous attacherons à vé-
rifier que chaque méthode fournit bien les résultats attendus ; ce qu’on appelle des
tests unitaires.

1
Comment tester un programme ?
Avant d’aborder JUnit, posons-nous la question des types d’erreurs qu’un programme
peut comporter, de ce que veut dire tester un programme et pourquoi une automatisation
est nécessaire.
1.1
Les types d’erreurs
Un programme peut mener à trois sortes d’erreurs 1 :
1. il peut ne pas compiler ;
2. il peut se planter à l’exécution (par exemple si on demande une division par 0) ;
3. il peut fournir un résultat incorrect.
Le 1er cas est facile à détecter puisqu’il suffit au développeur de demander une compila-
tion 2 pour obtenir la liste complète des erreurs de ce type.
Les deux derniers cas sont plus délicats. Comment savoir qu’on a bien testé toutes les
parties de code ? Qu’on a bien testé tous les cas particuliers ? Cela demande une réflexion,
une planification des cas à tester.
1.2
Tester quoi et quand ?
Commençons par quelques réflexions sur les tests.
1. Nous allons tester chaque méthode séparement. L’idée est que si toutes les
méthodes sont correctes, le programme le sera aussi 3.
2. Pour chaque méthode, il faut imaginer tous les cas qui pourraient poser pro-
blème. Concrètement, il faut trouver les paramètres à donner à la fonction pour
que tous les cas particuliers soient testés. Par exemple, si une méthode doit
réagir différement si son paramètre est négatif ou pas, il faudra au minimum la
tester avec un nombre négatif et un nombre non négatif.
3. Dans une situation réelle, une application est composée de milliers de méthodes.
Si chacune nécessite quelques tests, le nombre total de tests est colossal.
4. Lorsqu’on apporte une modification dans le code (pour le corriger, le rendre plus
lisible ou parce qu’on ajoute une fonctionnalité) il est possible qu’on crée une erreur
là où il n’y en avait pas. Pour être sûr, il faut dès lors tout retester.
On comprend bien qu’il faut mettre en place une procédure de tests la plus rapide
et facile possible si on veut pouvoir l’exécuter régulièrement. Pour toutes ces rai-
sons, tester à la main chaque cas planifié n’est pas envisageable ; une seule solution :
l’automatisation.
Automatisation des tests Automatiser les tests revient à écrire du code de
test dont le but est de tester le code de l’application.
1. À coté de ça, il peut avoir des défauts sans être faux à proprement parler. Cela peut impacter le
développeur (s’il est peu lisible) ou l’utilisateur (s’il est trop lent, trop gourmant en mémoire ou peu
convivial)
2. Explicitement ou implicitement lorsqu’on l’exécute.
3. Ce qui n’est que partiellement vrai. D’autres tests, comme des tests d’intégration pourront
suivre pour vérifier que les différentes parties du programme communiquent correctement entre-elles.

1.3
Une approche naïve
Imaginons pour l’instant que nous ne disposons pas de JUnit – que nous ne connaissons
pas encore de toute façon – et imaginons à quoi pourrait ressembler un code de test.
Pour être concret, imaginons que :
1. On a ajouté à la classe Dog une méthode sound() qui retourne le son fait par le
chien (plutôt que de l’afficher à l’écran).
2. On se calque sur la méthode bark pour dire que le cri dépend de son poids.
▷Yip yip s’il pèse moins de 10 kilos ;
▷Wouf s’il pèse entre 10 et 30 kilos (inclus) ;
▷WOUUUF s’il pèse plus de 30 kilos.
3. On voudrait la tester avec les poids : 9, 10, 11, 29, 30 et 31.
1.3.1
Appels successifs à la méthode à tester
Une première idée est d’appeler la méthode pour chaque cas et d’afficher la réponse.


Dog dog1 = new Dog("chien1", 9);
System.out.println(dog1.sound());
Dog dog2 = new Dog("chien2", 10);
System.out.println(dog2.sound());
// [...]


Cette approche nécessite de lire la sortie et de vérifier, au cas par cas, que chaque réponse
est correcte. C’est fastidieux, même pour quelques dizaines de tests.
1.3.2
Incorporation de la bonne réponse
Une amélioration consiste à inscrire la bonne réponse dans le code et à demander au
programme de vérifier qu’elle correspond à ce que la méthode retourne.


Dog dog1 = new Dog("chien1", 9);
System.out.println("Yip yip".equals(dog1.sound()));
Dog dog2 = new Dog("chien2", 10);
System.out.println("Wouf".equals(dog2.sound()));
// [...]


C’est déjà mieux mais cela nécessite de parcourir une longue suite de true à la recherche
des quelques false qui s’y sont glissées. Ça reste fastidieux et source d’erreurs.
1.3.3
Filtrage du résultat
Finalement, ce qui nous intéresse, ce sont les cas d’erreurs ; on peut n’afficher que ceux-là.


Dog dog1 = new Dog("chien1", 9);
if (!"Yip yip".equals(dog1.sound())) {
// Afficher des détails sur l'erreur : cas testé, valeur attendue, valeur réellement reçue...
}
Dog dog2 = new Dog("chien2", 10);
if (!"Wouf".equals(dog2.sound())) {
// Afficher des détails sur l'erreur : cas testé, valeur attendue, valeur réellement reçue...
}
// [...]


C’est déjà beaucoup mieux ! Malgré tout, ça nécessite de récrire constamment des codes
similaires (comparaison et affichage d’un rapport d’erreurs). On pourrait écrire une fonc-
tion qui fait le boulot mais Junit va le faire mieux que nous. On pourra se concentrer
sur ce qu’il faut tester et lui s’occupera de tous les aspects pratiques.

JUnit
JUnit est le framework le plus utilisé pour les tests unitaires en Java.
Framework
Plus qu’une simple bibliothèque, un framework définit une boite à outils qui facilite
le développement d’une application tout en imposant un cadre à son architecture.
JUnit ne fait pas partie de la bibliothèque standard de Java. Toutefois, il est parfaite-
ment connu par IntelliJ qui l’installera, d’un simple clic, lors de la première utilisation.
La dernière version en date est Junit 5. C’est celle que nous utilisons à l’école et que
nous vous conseillons également de choisir chez vous.

Anatomie d’un test
Que peut-on remarquer sur une méthode de test ?
▷Chaque cas de test est implémenté par une méthode dédiée.
▷Cette méthode de test est annotée par @Test afin d’être reconnue par Junit.
▷Elle ne prend aucun argument et retourne toujours void.
▷Son nom est quelconque mais il est bon d’être le plus possible explicite car
il sera utilisé dans le rapport en cas d’erreur. Nous vous suggérons d’utiliser
le nom de la méthode testée, suivi d’une explication du cas testé. N’ayez pas
peur des très longs noms, vous ne devrez jamais le retaper.
▷Il contient une ligne qui précise le test à faire.
1
assertEquals( "Yip yip", dog.sound());
Cette ligne affirme (et donc demande de vérifier) que la réponse attendue
("Yip yip") est bien égale à ce que renvoit l’appel dog.sound().
Il est important de mettre d’abord la réponse attendue, suivie de l’appel,
pour que le rapport soit compréhensible en cas d’erreur.
L Il n’y a plus qu’à lancer le test. Pour ça, exécutez normalement la classe de test.
Vous devriez voir un rapport qui indique que tous les tests (1 sur 1) sont passés.

2.2
Cas particuliers
L’essentiel de l’utilisation de Junit a été dit. Il reste juste quelques concepts qui vont
vous permettre de faire face à toutes les situations que vous allez rencontrer en Dev2.
2.2.1
Une méthode qui retourne un booléen
Si une méthode retourne un booléen (comme la méthode isHungry()), on pourrait écrire


assertEquals( true, dog.isHungry() )
assertEquals( false, dog.isHungry() )


mais il existe deux méthodes dédiées pour ces situations ; préférez-les !


assertTrue( dog.isHungry(....) )
assertFalse( dog.isHungry(....) )


2.2.2
Une méthode qui lance une exception
Une méthode peut lancer une exception si elle ne parvient pas à faire ce qui lui est
demandé ; typiquement parce que les paramètres ne sont pas valides. Cela fait partie des
tests de vérifier qu’une méthode lance bien une exception (et la bonne) quand elle doit

le faire. Mais comment puisqu’il n’y a aucune valeur de retour à tester ? Une méthode
qui teste un exception s’écrit ainsi 4 :


assertThrows(IllegalArgumentException.class, () -> new Dog("chien", -1));


On teste que le constructeur d’un Dog refuse bien un poids négatif.
2.2.3
Une méthode qui modifie l’état
Certaines méthodes ne retournent rien (void) mais modifient l’état de l’objet. Dans ce
cas, on ne teste pas la valeur de retour (inexistante) mais l’état de l’objet après l’appel.
Idem pour le constructeur. Par exemple, les lignes suivantes vérifient que le constructeur
assigne bien le nom.


Dog dog = new Dog("chien", 9);
assertEquals( "chien", dog.getName() );


2.2.4
Une méthode qui retourne un nombre flottant
À cause de la précision finie des processeurs, il est délicat, lorsqu’on compare deux
nombres flottants (non entiers) d’utiliser une égalité stricte. Junit a prévu de pouvoir
préciser l’écart admis entre la réponse attendue et la réponse retournée.


assertEquals( -1, Math.cos(Math.PI), 0.000001 );


Ici, on vérifie la méthode cos de la classe Math fournie par la bibliothèque standard. On
teste que le cos (π) est bien -1 en admettant un écart à partir de la 6e décimale.
2.2.5
Les entrées-sorties
Si une méthode est censée afficher du texte à l’écran, il faudrait vérifier que ce texte
s’affiche vraiment. C’est possible mais plus compliqué.
De même, si une méthode demande des valeurs à l’utilisateur (lectures au clavier), il est
plus difficile de la tester.
En Dev2 on ne vous demandera de tester ni des lectures ni des affichages.
2.2.6
L’aléatoire
Comment tester une méthode qui produit un résultat aléatoire ? Pensez à la méthode
run() developpée dans le TD3 où le chien se blesse une fois sur cinq. Pour notre test,
impossible de savoir si le chien doit être blessé ou pas après avoir couru.
En fait, les programmes utilisent du pseudo-aléatoire. Il s’agit de méthodes qui donnent
l’illusion de l’aléatoire mais générent des nombres suivant un algorithme tout-à-fait
déterministe (mais non prédictible). On peut contrôler ce pseudo-aléatoire en fixant la
graine (seed) qui est la valeur qui sert d’amorce pour générer les nombres. Nous allons
éviter ce genre de tests en Dev2.
4. Vous allez peut-être tomber sur une autre syntaxe lors de vos recherches. Attention ! Il s’agit
probablement d’une vieille syntaxe qui était la seule valable avec les anciennes versions de Junit mais
qui n’est plus recommandée.

3
Plan de tests
Jusqu’à présent, nous avons ajouté quelques tests par-ci par-là sans y avoir vraiment
réfléchi. Pour être sûr de bien tout tester et de ne pas passer à coté d’erreur, il faut
palnifier nos tests.
Il serait tentant de limiter les tests. Moins il y en a, moins on trouvera d’erreurs
dans notre code, ce qui n’est jamais agréable pour notre égo. Il faut pourtant se
forcer : le moi testeur doit tenter de mettre en défaut le moi codeur.
Couverture de code
La couverture de code est le pourcentage des lignes de code qui sont effectivement
testées, c’est-à-dire qui sont “visitées” par Java lors de l’exécution des tests fournis.
Il faut viser une couverture de 100% mais ça ne suffit pas à garantir qu’on ne rate
rien.
Lorsqu’on imagine un plan de tests il faut avoir à l’esprit les erreurs les plus
communes qui sont commises quand on programme et imaginer les tests qui vont
nous en prémunir en les détectant. Parmi les erreurs courantes, citons :
▷Se tromper dans une comparaison en écrivant < au lieu de > (et vice-versa).
ou encore <= au lieu < (et vice-versa).
▷Se tromper dans un long test en mettant un ET à la place d’un OU (et
vice-versa).
▷Se tromper dans le parcours d’un tableau ou d’une partie de ce tableau, en
commençant trop loin ou en s’arrêtant trop tôt.
▷En oubliant un this dans un constructeur ou un setteur ce qui a pour effet de
ne pas assigner un attribut (un bon IDE nous signale ce genre d’erreur).

Tests et refactoring
On passe généralement plus de temps à lire/adapter/déverminer du code existant qu’à
l’écrire. Cela implique que le temps passé à simplifier son code – le rendre plus lisible –
se traduit en gain de temps lors d’une modification ultérieure.
Refactoring
Le refactoring (on dit aussi réusinage de code ou remaniement) est l’opération
consistant à retravailler le code source d’un programme informatique – sans toute-
fois y ajouter des fonctionnalités ni en corriger les bogues – de façon à en améliorer
la lisibilité et/ou la modularité afin de faciliter sa maintenance et son évolution.
Pourtant, il est dangereux de modifier un code qui fonctionne. Ne va-t-on pas introduire
des erreurs ? Les tests unitaires vont justement nous permettre d’aborder cette opération
en toute sérénité ; on apporte une légère amélioration au programme, on relance tous
les tests et, si tout passe toujours, on peut poursuivre l’amélioration de notre code. Dès
qu’une erreur apparait, c’est qu’on vient juste de la commettre et on pourra facilement
la corriger.
5. En laissant tomber la blessure aléatoire et l’affichage qui est plus difficile à tester.

Développement dirigé par les tests
Développer un code conséquent est une tâche difficile. Nombreux sont les projets in-
formatiques qui n’ont jamais abouti malgré les millions d’Euros et les milliers d’heures
investies. Pour se donner les meilleures chances d’aboutir, il faut suivre une méthodo-
logie éprouvée et vous aurez des cours de gestion de projets qui vous apprendront les
bonnes pratiques.
Un aspect des méthodologies Agile – qui sont fort utilisées pour le moment – est ce qu’on
appelle le TDD (Test Driven Development). Avec cette approche, on écrit d’abord le
test pour une nouvelle fonctionnalité avant le code qui l’implémente. Alors bien sûr, au
début, le test échoue. Le but du jeu est de le faire réussir en apportant la modification
nécessaire dans le code. Une fois que c’est fait, on passe à la tâche suivante.
